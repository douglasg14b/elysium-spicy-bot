# Chat agent

BrattyBot's conversational side: a tool-calling agent (Vercel AI SDK `ToolLoopAgent`, models on OpenRouter) that answers when someone @mentions the bot or replies to something it said, and can look things up on the server before it answers.

**When it speaks — and when it doesn't:**
- An @mention, anywhere.
- A reply to a chat agent post, outside tickets. Never a reply to the bot's automated posts (onboarding questions, ticket controls, flow messages, level-ups, birthdays).
- **In a ticket, only an explicit @mention, and only to answer a genuine question about the server** — otherwise the agent calls `stayQuiet` and nothing is posted. It never joins a ticket unprompted. Replaced the old `ai-reply` feature (deleted 2026-11-09); plan and later steps in `docs/plans/chat-agent-v2.md`.

## One turn

1. `trigger/triggerGate.ts` — is this message for us? `<@bot>` in the text, or — outside a ticket (`findLiveTicket`; a thread counts as its parent ticket) — a reply to a chat agent post (`isChatAgentPost`: a bot reply that answers a message addressed to the bot; other bot replies, like the "hello there" easter egg, don't count). The reply chain is fetched only for a reply to the bot.
2. `chatAgentHandler.ts` — skips channels the bot cannot post in; holds the member to `safety/rateLimit.ts` (4 turns a minute, then one in-character warning and five minutes ignored).
3. One turn per channel at a time, in order (`createPerGuildQueue` from `src/shared/perGuildQueue.ts`, keyed by channel); past 3 waiting in a channel, new turns are dropped and logged.
4. `tools/chatToolContext.ts` (`buildChatToolContext`) — server, channel, asker, whether the asker may read the channel's history, the channel's ticket if it is one, and the server's config — its context channels, intros channel, the admins' rules and notes, and who is staff to the agent (its own staff roles, else Server Settings': `agentStaffRoleIds`) (`data/chatAgentConfigRepo.ts`, read once per turn).
5. `session/discordHistory.ts` → `session/historyToModelMessages.ts` — the channel's newest 40 messages, up to now, with the one being answered marked `→` (so a queued turn sees the reply the turn before it posted). An asker who cannot read history gets only their own message, and none of the session.
   Discord is the source of truth for what people said; the **session** (`session/chatSessions.ts`, persisted by `data/chatSessionsRepo.ts`) keeps only what Discord cannot — each turn's question, answer (as posted, mentions turned back to names), tool calls and results, the model that wrote them, who could read it and every channel all of them could see. A mention or a reply to the bot starts one; every turn after it in the channel, whoever asks, carries it on until it ends: an hour with no turn, or 45 other messages in the channel since the bot's last reply in it. A reply to one of a session's posts carries it on anyway, for a day after its last turn; a session is deleted a day after its last turn (swept after each turn and hourly), and keeps its newest 20 turns. A session that cannot be read starts the turn afresh, and a failed write is only logged. Deleting a turn's question or post deletes the turn (`initChatAgent`'s delete listeners); a turn whose question or post is missing from inside the window is skipped, for a delete the bot missed. `session/sessionReplay.ts` decides what of it this turn sees: a turn's trace only while **every reader now was a reader then**, they can all still see every channel they could then, and the same model reads it (else its question and answer, posted where everyone here can scroll to them); a turn that asked a staff-only tool only while every reader is still staff — whole or not at all. A turn whose reply is in the window is spliced in place of it; older ones come first. Trimmed newest kept first against two budgets — 16k characters of chat, 60k of traces — never dropping the marked message or what follows, and never opening on an assistant turn: once the chat budget is spent, older traces still come in, any whose question did not make it led by it, and a trace too big for what is left loses its largest results to a note (`session/fitTrace.ts`) before it falls back to its text.
6. `agent/runChatTurn.ts` — the agent, built per turn: `agent/persona.ts` + mode (`social`, or `ticket` when the channel is a ticket) + the admins' rules and notes, when written + facts (`agent/chatInstructions.ts`), the tools, up to 6 steps and 90 s (16 and 3 minutes where every reader is staff: `turnLimitsFor`).
7. `agent/runReviewedTurn.ts` + `output/replyReview.ts` — the output controls, each built from something a model did in the evals (`docs/chat-agent-model-evaluation.md`). Fixed in code: a copied chat-log prefix (`[time] BrattyBot:`, `→`) stripped, a reply quoted end to end unwrapped, emoji past 2 removed. Turned back: empty; a tool call written out as text; a pet name used to address someone; a `#name` that is no channel everyone here can see. A turned-back reply gets **one** redo — a second full turn that sees its own reply and why it was not posted — and if that is still wrong, the fallback line (except a made-up channel, which then posts without its `#`). In a ticket, empty or a written-out tool call is silence, with no redo. Each turn logs `outcome=` and any `redo=[…]`.
8. `output/linkReferences.ts`, then `output/replyText.ts` — the model never sees or writes ids: it writes `#name` and `@name`, and each name that means exactly one thing (a channel every viewer can see, a member, a role) becomes `<#id>`/`<@id>`/`<@&id>` — never inside code, never `@everyone`/`@here`; anything else stays as text. Linking comes before splitting, since links are longer. Then cleaned and split into at most two messages, each a reply to the message answered (only the first pings); posted with `allowedMentions: { parse: [] }` (plus the replied-to user), so the model can never ping anyone else. A half-posted reply keeps what posted; the failure line goes up only when nothing did. Failures are logged as one line — never the error object, whose request body is other members' messages. In a ticket, an empty answer or a failure posts nothing.

## Tools (`tools/`)

All read-only, all bound to the turn's `ChatToolContext` (server, channel, asker, ticket) — the model never names a server or acts as anyone else.

| Tool | Answers |
|---|---|
| `getServerRules` | the context channels marked as rules, else the guild's rules channel; last 20 messages each, naming the channel (cached 10 min) |
| `readContextChannel` | one of the server's other context channels, by name or id, the same way; its description names the ones the asker can read |
| `getServerInfo` | name, description, member count, boosts, role names |
| `listChannels`, `getChannelInfo` | channels by `#name` (no ids — no tool returns one), topics (cut to 150 in the list), categories, NSFW flag |
| `searchRecentMessages` | the current channel's last 100 messages |
| `getMemberInfo` | a member's roles/join date (member cache, then Discord's member search), and their `pronouns`: the names of their pronoun roles (`tools/pronouns.ts` — every slash-separated part a pronoun word, so `Dom/sub` is not one; or a name with "pronoun" in it), listed apart since the role list's cut of 15 by position drops low roles |
| `getUserLevel` | their level and XP (`loadUserLevelProfile`). **Staff only, where every reader is staff** (the owner's rule: levels and XP are not talked about in public), with its own refusal (`LEVEL_REFUSALS`) pointing members at `/level`, which answers privately |
| `getMemberIntro` | what a member wrote in the server's intros channel (Config below): their newest 3 posts, oldest first, each cut at 1,500 characters, mentions named for the readers (a channel only if all of them can see it). Only when every reader can read the intros channel; read from the copy in `chat_agent_intros`, never from Discord |
| `getTicketInfo` | this channel's ticket only |
| `getBotFeature` | `feature` (one of `BOT_FEATURES`): how one of the bot's own features works — its guide (`featureGuide.ts` beside the feature's code), dashboard links, the slash commands read off the real builders — and how this server has it set up, read live from the feature's repos as names (`tools/featureSetup.ts`). **Staff only, where every reader is staff** (`tools/staffAccess.ts`: one of the chat agent's staff roles — its own, set on its page, else Server Settings' (`agentStaffRoleIds`) — the owner or an Administrator — the asker and every other viewer; refused too while the server's member cache is short of its member count, since an uncached member is no viewer); otherwise it answers only why not and what to tell them, so nothing of the feature reaches the model to repeat. A channel in the setup is named only when every reader can see it; a ticket category is found by its id, and a slot with no category behind it is reported as stopping tickets. Links only when the dashboard is on (`WEB_ENABLED`). The admins' bot rules are returned word for word (the owner's "live config"; the dashboard already says they can be coaxed out) |
| `findTickets` | `query`: a ticket number, a member (every ticket of theirs, closed and deleted too; someone who has left by the names their tickets recorded), or a ticket's channel (#name, mention or link). Each ticket with its details and its `#channel` for `readChannelMessages`. **Staff only, where every reader is staff**, like `getBotFeature`. A ticket is described only to readers who could find it themselves: its channel seen by every reader, or — channel gone — every reader handles tickets (`memberHandlesTickets`: a moderation role or Moderate Members); the rest are only counted. Someone who has left is found by the names on tickets about them (`subjectOnly`); at most 10, with a note when there are older ones |
| `readChannelMessages` | `channel` (#name, mention, id, or a message link — a link starts *around* that message, marked `linked`), `before` (the last page's `continueBefore`): 50 messages a page, oldest first, through `describeContent`, each cut at 600 characters. **Staff only, where every reader is staff**, and only a channel every reader can see and read the history of, and the bot can read (`readableTextChannel`) — threads included, fetched by id from a link or an id (a thread comes back as its name under its `#channel`, since a thread is not linked); a link to another server, and a channel Discord says is gone or hidden from the bot, answer "no channel". 10 pages and 120,000 characters a turn, spent as each read starts, so calls made together cannot overrun it (counted by the tool, built per turn). A private thread's members are fetched before its viewers are counted (`buildChatToolContext`), since discord.js caches them only from events. The session keeps the pages read, so a follow-up answers from them without reading again — while every reader is still staff (`session/staffOnlyTrace.ts`; otherwise the turn is its question and answer). A turn where every reader is staff gets 16 steps and 3 minutes instead of 6 and 90 seconds (`turnLimitsFor`, `agent/runChatTurn.ts`), so the agent can page back until it has enough |
| `getChannelAccess` | `channel` (#name, mention, id or link; left out, the one asked in): who can see it today, worked out from its permissions — never from who has posted there. Each role that lets someone in, as if it were a member's only role (@everyone's permissions and its own, then the channel's overwrites for each; Administrator sees everything; bots' own roles left out) — or, a channel open to @everyone, only the roles it shuts out — and every person (not bot) who can see it by `memberCanSee`, staff first, marked `staff` (`isStaffMember`) and `addedDirectly` (their own overwrite, or a private thread's membership); 50 by name, the rest counted. A thread answers by its parent's overwrites; a private thread lets a role in only with Manage Threads, and its members are fetched first (`findAdmittedChannel`, which does so for every staff tool's lookup by id). **Staff only, where every reader is staff**, and only a channel every reader can see. The member cache is whole by then: the gate refuses while it is short |
| `stayQuiet` | tickets only (`activeTools`): say nothing; the loop stops on it |

**Every channel the agent reveals goes through `tools/visibleChannels.ts`, checked against everyone who will read the answer** — the asker and every member who can view the channel it lands in (`Viewers`): a moderator asking in `#general` gets nothing staff-only. Private threads need membership or Manage Threads on top of their parent's permissions; threads are left out of lookups. Reading a channel's messages (rules, context channels, the current channel's history, `searchRecentMessages`) also needs Read Message History for all of them. A `<#channel>` mention in any text the model sees is named only if all of them can see it. Going out, a `#name` becomes a link only for a channel all of them can see (`output/linkReferences.ts`). `tools/__tests__/visibleChannels.test.ts` and `session/__tests__/historyToModelMessages.test.ts` hold these.

## Trying it

- `pnpm chat-agent:eval [--model a,b] [--persona current,v1] [--scenario …] [--runs n] [--judge m] [--second-judge m]` — scored evals: behaviour checks plus an LLM judge on tone (brattiness band per scenario, lines crossed, voice), with each model's tokens and cost a turn and the judge's, as OpenRouter reports them. One run per scenario by default; a reply that fails a hard check is not judged. `--second-judge` grades the same replies alongside and reports how often it agrees — how to vet a cheaper judge. Needs only `OPENROUTER_API_KEY`; results in `.chat-agent-evals/`.

- `pnpm chat-agent:try [--model a,b,c] [--scenario …] ["your question"] [--ticket]` — fixed scenarios on a made-up server, side by side per model. Real prompt and tool schemas, canned tool results. Needs only `OPENROUTER_API_KEY` in `.env.local`.
- `pnpm chat-agent:try-live --channel <id> --as <userId> [--model …] "question"` — one turn against a real server with the real tools, printing the reply as it would be posted; posts nothing. Needs the bot's full env.

## Config

**Context channels** — per server, on the dashboard's Chat Agent page (`/chat-agent`; Administrators, like every page): up to 10 channels, each once, any of them marked as a rules channel. Stored in `chat_agent_config` (one row per guild, JSON `{ contextChannels: { channelId, isRules }[], botRules, serverNotes, staffRoleIds, introsChannelId }`; no row means nothing set; read through `chatAgentConfigSchema`, so a row from before a field existed reads as its default). The PUT (`logic/saveChatAgentConfig.ts`) writes the whole config and takes only text channels of that server the bot can read. Marked rules channels replace Discord's rules channel in `getServerRules` — even when the asker can read none of them; with none marked it falls back to Discord's. The rest are what `readContextChannel` reads. Each is read only for an asker who can see it and read its history.

**Staff roles** — the roles whose members count as staff for every staff-only tool above, the session replay's "still staff" and `getChannelAccess`'s `staff` mark. Separate from Server Settings' staff roles (who may run the dashboard and what a flow's `staff` audience compiles to), so moderators can be staff to the agent without being staff there. Left empty, the agent uses Server Settings' (`agentStaffRoleIds` in `tools/chatToolContext.ts`, the one place either list is read for a turn). Saved as Server Settings saves its own: deduplicated, and a newly added id must be an assignable role (`isAssignableRole`); one saved before and deleted since is kept, so the page stays saveable. Tickets' moderation roles are a third list, untouched.

**Intros channel** — one text channel members introduce themselves in. `intros/introsSync.ts` (not a stage of a turn: a background copy, wired by `initChatAgent`) keeps a copy of it in `chat_agent_intros` (one row per post: a member's own, non-reply, with text): each post as it lands, is edited (a partial is fetched first) or deleted, and the whole channel again — newest first, 100 pages at most, one server at a time across the bot — at `ClientReady` for every allowed server that has one, on `GuildAvailable` for one that was out, and when a save changes it. A rescan neither overwrites nor prunes a post the live listeners touched while it ran (`noteLiveWrite`), since theirs is the newer word (`introsChannelSaved`, called by `saveChatAgentConfig`, the one write path; it also drops what was held from the old channel). Only a read that reaches the channel's first message drops posts deleted while the bot was away. Which channel each server picked is held in memory, so a message elsewhere costs no database read. A forum is not supported (the picker offers text channels).

**Pronouns** — Discord shows bots no one's profile pronouns or bio, so the agent has a member's pronoun roles and what they wrote in their intro. The instructions (`PRONOUNS` in `agent/chatInstructions.ts`, beside the tool rules rather than in the persona, so the evals' persona swap keeps it) say "they" by default and whenever it reads naturally, and another pronoun only once looked up; the asker's pronoun roles are in the facts (`Speaking to you: Vex (pronouns: she/her)`) so the commonest case needs no call.

**Bot rules and server notes** — two free texts on the same page, each trimmed and at most 2,000 characters (`MAX_GUIDANCE_LENGTH`). Both go into **every** turn's instructions, after the persona and the mode (`adminGuidance` in `agent/chatInstructions.ts`), fenced in `<admin-instructions>` / `<admin-notes>` so the model reads them as the admins' words: rules are followed in its own voice but cannot lift any line above them (persona, tool use, ticket mode), and are told apart from the server's rules, which stay `getServerRules`'s; notes are facts it may repeat to anyone (the page says so), a tool's live answer wins over a note that disagrees, and in a ticket a question the notes answer counts as one it may answer. Not a tool on purpose — a model that has to decide to look them up would sometimes not. They cost tokens on every reply, hence the cap. The request schema and the page both judge the trimmed text. The PUT writes the whole config with no stale check: of two saves touching the same field, the last wins. Admin text is passed on as written — a channel it names is not checked against who will read the answer (a name some readers cannot see trips the made-up-channel redo, and is posted without its `#`); the page tells admins both texts can reach anyone. A save sends only the fields changed on the page over the latest load. Evals: `admin-note`, `admin-rule`, `admin-rule-overreach`, `admin-rules-vs-server-rules`, `ticket-admin-note`.

`CHAT_AGENT_MODEL` (OpenRouter slug, default `mistralai/mistral-large-4-0` — chosen in `docs/chat-agent-model-evaluation.md`), with `OPENROUTER_API_KEY` / `OPENROUTER_BASE_URL`. OpenRouter picks the upstream provider; no data-collection preference is set yet (open question in the plan).
