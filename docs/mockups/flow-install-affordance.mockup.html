Install / uninstall — the affordance, then the dialog

Two problems, addressed separately. Same data and same endpoints throughout; only the presentation changes.

Critique 1 — “Install” and “Installed” side by side is two buttons for one concept, and “Installed” reads as a status, not an action. Nothing says click here to remove what I provisioned.
Critique 2 — the shipped dialog dropped too much. It reads like an admin panel a programmer laid out: a flat list of badges, no hierarchy, no weight on the thing that matters.

Part 1 — one button that knows what state it’s in

The flow either has resources in the server or it doesn’t. That is one fact, so it gets one control whose label, colour and icon follow the fact. Nothing about a flow with nothing installed should offer to uninstall, and nothing about a fully installed flow should lead with “Install”.

Today — what shipped, and what the critique is about

Two verbs for one concept. “Installed” is an adjective — it describes a state, so it reads as a label that happens to be clickable. Both are always present regardless of what is actually in the server.

Proposed — state A: declared, nothing in the server yet

One button, one verb. The count is what you’d get. No uninstall offered, because there is nothing to uninstall.

Proposed — state B: everything it declares is live (the common case, and the one that was broken)

👁See what’s in your server 4 resources, 1 button message
↻Reinstall missing pieces Rebuilds anything deleted by hand
⌫Uninstall from server Deletes the 2 it created

The button states the fact (installed) and the caret promises actions behind it — the standard split-button read. “Uninstall” is a verb, sits under a destructive colour, and says what it will take. Clicking the button face opens the dialog; the menu is the shortcut.

Proposed — state C: partly installed, or declarations changed since

Drift gets its own face rather than hiding behind “Install”. This is the state an operator most needs told about and currently cannot see at all.

Why a split button rather than two peers. Install and uninstall are not siblings — they are the two directions of one reversible operation, and which one is available depends entirely on current state. A permanent pair forces the operator to work out which applies; a state-aware control answers that for them and puts the rarer, destructive direction one deliberate click deeper. The badge count does the job “Installed” was failing to do: it tells you there is something there before you click.
  • Cost: uninstall is no longer a single click. That is the intent — it deletes real channels.
  • Needs: the builder must know install state on load. Today it only asks when the dialog opens, so this adds one /published fetch on mount.

Part 2 — the dialog, with design in it

Same information as the shipped version, arranged so the eye lands on the consequence first. Kind is carried by a coloured glyph instead of a text badge, nesting is shown by indentation rather than stated, and the two fates are separated into groups so “what dies” is a region rather than a word repeated down a column.

What shipped Rejected

Flat rows, uppercase badges, fate as a right-aligned word. Every row weighted the same, so nothing guides the eye. No grouping, no hierarchy, no relationship between the category and the channel inside it.

What changed, and why each one.
  • Consequence in the header. One sentence naming what uninstalling costs, so the answer is readable before the list is.
  • Two groups, not one list. “What dies” becomes a region you can see the size of at a glance. The fate word stops being a column to read down.
  • Coloured kind glyphs (▤ category, # channel, @ role) replace uppercase text badges — same information, far less ink, and consistent with the resource-declaration mockup.
  • Nesting is drawn. The channel sits inside its category, which is also why deleting the category is a bigger deal than the row suggested.
  • Actions move to a footer bar and separate by direction: reversible on the left, destructive on the right, “Done” between them. They were inline mid-body before.
  • “Uninstall 2” carries its count, so the button itself is the last confirmation before the confirm step.
